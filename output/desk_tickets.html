What I learned about planning

  • The money predictions were exact. I wrote $3,400 → $2,552 → $152 and "no spending on #103", and the Cash tab landed on exactly those numbers. Cash flow is deterministic because the rules live in code (the pay tool), not in the model.
  • I planned a careful one-specialist-first chain; the Boss fans out instead. Its prompt literally says to call several delegates in one turn when work is independent, and it treated everything as independent. On #102 that was harmless, because there was only one sensible specialist. On #101 and #103 it caused duplicate work and the draft race.
  • I planned single passes; reality is multi-pass. Every money step needs a human, so every approval means another run. 8 runs for 3 tickets isn't the agents' fault; it's the human-in-the-loop design.
  • I didn't plan for state carrying over between tickets. #101 paying invoice 501 changed the facts for #103. A good plan should be written in run order and update the shared state: cash and vendor blocks.

3 · What would have been simpler as one agent with tools

Honestly, most of this run. All five agents call the same MCP server on the same database with the same model. Delegation adds a prompt, a full agent loop and a report for every hop.

TicketOne agent would just…Why that's simpler here
#102get_rent_due(1) → get_cash → request_rent_payment(1) → update_ticket_status.4 tool calls instead of 3 agents and 2 handoffs. Nothing in a rent notice needs a "specialist"; the lease row already has the amount, landlord and date.
#101check_stock → list_vendors → request_invoice_payment(501) → (human) → request_purchase_order → (human) → draft_customer_message.This ticket is a strict chain: stock decides vendor, vendor decides invoice, invoice decides PO. Parallel specialists can't help with a chain. They just re-check each other (Accounting ran get_invoice_status and get_cash again after Inventory already had them) and ran Accounting twice at once.
#103check_stock → get_pricing → check_margin → get_cash → request_price_override → one draft.The wrong "no discount pending" draft only happened because two agents ran in parallel and one read the state before the other wrote it. One agent writes the request, then writes the draft. Race gone.

What the team still bought me, and why I'd keep some of it:

  • Least privilege by role. Only Accounting can call request_*; only Customer Service writes drafts; only the Boss sets status. But the real safety comes from the MCP pay tool and the human gate, which hold whether there's one agent or five.
  • Readable accountability. The round table and the shift report show who decided what, and Customer Service's italic letters read differently from Accounting's ledger voice. That's good for a human sitting at the desk, but it's a UI benefit, not a correctness one.
  • Context isolation. Each specialist starts clean, so a long #103 run doesn't stuff Accounting's prompt with Customer Service's drafts. With only 3 tickets that never mattered.

My redesign: one "desk" agent with all the agent tools for routine tickets (rent, simple orders), and a second agent only where independent judgment helps. The Boss would delegate in sequence, not all at once, and get a per-ticket token budget.
